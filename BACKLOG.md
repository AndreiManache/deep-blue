## Personal food database (2026-08-27)

- [ ] **Bigger, riskier idea, flagged honestly: skip the LLM call entirely for confident repeat foods, to actually reduce cost.** Important distinction from the above: the existing system already avoids trusting a *fresh guess* for known foods, but it does **not** currently save any LLM cost, because the model still runs its full reasoning on every turn regardless of whether the server ends up using its number — the expensive part is understanding the sentence ("I had two eggs and a coffee"), not guessing the calories. Actually bypassing the model for a turn is a real architecture change with real risk (misparsing a turn that only *sounds* like an exact repeat, e.g. missing "...and also skipped lunch" tacked onto what looks like a simple repeat). Worth exploring later — e.g. a narrow, high-confidence fast path for near-verbatim repeats of a personal favorite — but should be scoped and built as its own careful feature, not assumed to fall out of the database work above.

## Performance & cost

- [ ] **Admin panel's "usage" dollar figures are our own estimate, not real provider billing — caused real confusion 2026-09-01.** Andrei saw ~$5 of estimated usage after a testing session, checked ElevenLabs' actual dashboard, and found $0 spent — because that account is on a flat-rate Starter subscription (40,000 included credits/month), and the testing only ate into the already-paid quota rather than triggering any pay-as-you-go overage. `usageCost.ts`'s reference prices (explicitly commented "for an ESTIMATE only") are built for pay-per-use pricing and don't know a user might be on a subscription plan with included quota, so the dollar figure can read as a real charge when it isn't one. Fix options, not yet scoped: (a) simplest — relabel the admin panel's numbers as "estimated pay-as-you-go cost" rather than bare dollar amounts, so it's clear this isn't a real bill; (b) actually pull real usage/balance from each provider's billing API where available (ElevenLabs, Gemini, etc.) instead of estimating from logged bytes/tokens — more accurate but real integration work per provider, and some providers may not expose this via API at all.
- [ ] **Reduce voice-turn latency further — streaming and/or skip the second LLM call.** Real root cause of the *bad* latency (18-45s spikes, tickets #25/#31) turned out to be neither of these — it was an unpaid Gemini billing balance silently throttling every request, found and fixed 2026-09-04 (switched to `gemini-3.8-flash` at the same time, both for the throttling investigation and for better instruction-following — see ticket #32). Confirmed baseline is now a healthy, consistent ~3s/turn (includes Murf TTS). Both levers below are genuinely optional now, not urgent fixes for a broken baseline:
  - **Stream the reply into TTS** — speak the first sentence while the rest generates and/or streams from the TTS provider, instead of awaiting the full text then the full audio file. Biggest remaining perceived-speed lever; real engineering lift (Murf's `/v1/speech/stream` endpoint already streams audio bytes — see `ttsMurf.ts` — the missing half is streaming the *LLM* output into it incrementally).
  - **Skip the second Gemini call for a logged turn.** Every log_food turn currently makes two sequential model calls: one to decide the tool call, one more to phrase the confirmation reply. Since the logged result is already known server-side after the tool runs, that confirmation could be templated (or a short deterministic sentence) instead of model-generated, roughly halving LLM latency again. Real tradeoff: loses the model's natural phrasing/personality in the reply, and needs a Romanian template too — a deliberate quality decision, not a free win.
  - The admin panel's Response-time card (avg + p95, shipped 2026-09-04) is the ongoing reality-check — watch that before assuming either lever is worth the complexity.
- [ ] **10-15 second latency logging from a photo (ticket #25) — likely improved by the 2026-09-04 billing fix, not separately re-measured.** The general voice-turn latency this shared a root cause with (an unpaid Gemini billing balance throttling every request) is fixed and confirmed healthy, but the vision/photo path specifically hasn't been re-timed since. Worth a quick re-check before assuming it's still slow.

## Mobile / native shipping

- [ ] **Native / Capacitor migration.** Would fully fix mic permission (one-time OS grant, all browsers) and give reliable speech via Apple's `SFSpeechRecognizer` + explicit audio-session control. Does NOT fix latency by itself. Cost: App Store friction + loss of instant deploy (Capacitor mitigates via OTA JS updates), device toolchains; backend unchanged. Recommended path if web STT ever proves unfixable: **Capacitor** (wraps the existing React app). Don't full-rewrite.
- [ ] **Premium native-experience bundle — explicitly deferred until the native migration (2026-09-04, Andrei's request).** Andrei wants a premium, native-feeling experience and raised several specific ideas. All of these are blocked by the PWA/native boundary and are being deliberately postponed until Deep Blue goes native (via Capacitor), rather than emulated with throwaway PWA hacks in the meantime — Andrei's own call, and the right one, since PWA-only workarounds for these would be discarded on migration:
  - **Real haptic feedback** on tap / log / confirm. iOS Safari + standalone PWA do **not** support the Vibration API at all (works on Android only), so this genuinely cannot ship on his iPhone as a PWA. Native (Capacitor Haptics plugin) does it properly.
  - **True lock-screen / home-screen widget** for one-tap food logging without unlocking. Impossible in a PWA — needs native WidgetKit. (PWA-side stopgap if ever wanted before migration: an iOS **Shortcut** deep-linking into a quick-log screen, reachable from Control Center on the lock screen. Not logged as a task, just noted as the only pre-native option.)
  - **Dynamic Island / notch treatment** — e.g. an app-colored progress indicator near the camera during a refresh/log, inspired by how Uber shows driver ETA there. The Island is native-only (ActivityKit Live Activities) and no app can literally "ring the camera." Closest achievable, and only *after* the black-translucent status-bar migration below: an animated app-colored strip across the top safe-area during refresh.
- [ ] **Status-bar / safe-area migration to `black-translucent` (2026-09-04).** Currently `apple-mobile-web-app-status-bar-style: default`, which makes the iOS status-bar strip a system-painted opaque bar *outside* the web viewport (`safe-area-inset-top` is 0) — so the detail-modal backdrop physically cannot dim that top strip, leaving a visible undimmed band (Andrei caught it in a screenshot). The only real fix is switching to `black-translucent` so web content flows edge-to-edge under a transparent status bar and the overlay covers everything; requires adding `env(safe-area-inset-top)` padding across all ~11 top-level screens (best done once at the app shell) so headers don't slide under the notch. App-wide change, hard to fully verify without a real notched device — deferred pending Andrei's go-ahead on the blast radius. Also the prerequisite for the top-safe-area refresh animation in the bundle above.
- [ ] **Swipe-back from anywhere on screen (2026-09-04).** Currently "back" is view-state (not history), and there's no in-app horizontal-swipe-to-go-back at all — iOS's own edge-swipe doesn't apply to this single-view app. Andrei wants a left-to-right swipe starting anywhere (not just the far-left edge) to trigger back. Achievable in the PWA now (a horizontal drag handler on screens that have a back button); transfers cleanly to native. Small, self-contained.
