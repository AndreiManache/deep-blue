# Deep Blue — Backlog

Ideas and open items to consider going forward. Shipped/completed work has been pruned — see git history for what's already done.

## Feedback & admin (from the friends-beta rollout, 2026-08-27)

- [ ] **Entry-correction capture with reason + evidence.** When a user edits an entry's calories, capture *why*, not just the new number. Context: the "users guardrail the entries" idea already works today — [foods.ts](server/src/foods.ts)'s food-knowledge base treats every calorie edit as a `"correction"` observation (stronger than a model `"estimate"`), remembers it as that user's `"yours"` value for the same food going forward, and promotes a food to crowd-`"verified"` once ≥5 users' corrections cluster within ±15% (`recordObservation`/`getConsensus`/`resolveNutrition`). What's missing is *reasoning* and an *audit trail* — no signal on whether the model misjudged portion size, misidentified the food, or was just genuinely ambiguous, and no way to check whether "5 people agree" actually means "5 people are right." **Proposed design**: when calories/macros are edited, show a lightweight, skippable one-step prompt — quick-select reason chips ("Wrong portion size" / "Wrong food or recipe" / "I have the real nutrition label" / "Just a typo, skip this") plus an optional evidence URL field (a link to a label/menu page — cheap, no storage infra needed, unlike a photo). Store as a new `entry_corrections` audit table (entry_id, user_id, food_key, old/new values, reason, evidence_url, created_at) — additive, doesn't touch `food_observations`. Surface in the admin panel as a "Corrections" list, same pattern as the feedback inbox. **Stretch**: an admin "trust this" action that promotes an evidenced correction to verified immediately, bypassing the 5-user threshold. **Deferred**: photo evidence — reuse the feedback-audio storage pattern if/when photo upload gets built for feedback too, don't build image storage twice.
- [ ] **Full "see all users and their behavior" admin panel.** Bigger scope than the feedback inbox (new tables/queries for engagement, not just a list to triage), and there isn't enough real usage yet to make a dashboard worth building. Interim: Railway SSH access to the production SQLite file already lets Andrei run one-off queries directly (`... | railway ssh -- node`) — e.g. `SELECT COUNT(*) FROM users`, `SELECT user_id, COUNT(*), MAX(created_at) FROM food_entries GROUP BY user_id` for who's logging and how recently, `SELECT username, created_at FROM auth_sessions ORDER BY created_at DESC` for recent logins. Manual and ad-hoc, but sufficient for occasional spot-checks during a small beta.
- [ ] **Per-user API cost/usage logging.** Log Claude token counts and ElevenLabs (STT+TTS) usage per `user_id`/session in the DB, so a runaway user or a bug causing loops is visible per-account, not just as a total spend surprise. Ties into the admin panel above once that gets built. Until then, spending/usage alerts on the Anthropic Console and ElevenLabs dashboard are the cheap interim guardrail.
- [ ] **Image upload for feedback reports.** Feedback capture shipped with text + voice + optional diagnostics-log attach; images need their own storage/upload endpoint (unlike voice, which reused the existing `MediaRecorder` pattern almost for free). Add once friends actually ask for it.

## Performance & cost

- [ ] **In-app cost tracker.** Log per-turn usage — Claude input/output tokens (the API returns `usage`), ElevenLabs TTS characters, and STT audio seconds — into a small table, apply unit prices, and show a running today/this-month estimate by provider on the Dashboard. It's an *estimate* (authoritative numbers live on each provider's own dashboard). ## Mobile / native shipping

- [ ] **Native / Capacitor migration.** Would fully fix mic permission (one-time OS grant, all browsers) and give reliable speech via Apple's `SFSpeechRecognizer` + explicit audio-session control. Does NOT fix latency by itself. Cost: App Store friction + loss of instant deploy (Capacitor mitigates via OTA JS updates), device toolchains; backend unchanged. Recommended path if web STT ever proves unfixable: **Capacitor** (wraps the existing React app). Don't full-rewrite.
- [ ] **Ship as a PWA (installable, offline shell).** There's already a `manifest.webmanifest` and icons under `web/public/`; needs verifying/completing the manifest (name, theme/background color, display `standalone`, icon sizes incl. maskable), a service worker for the app-shell (cache the built JS/CSS/HTML so it opens offline and launches fast), and the `<link rel="manifest">` + apple-touch-icon/meta tags in `index.html`. Note: installing as an iOS PWA does **not** reliably persist microphone permission — this is for installability/launch/offline shell, not a mic-prompt fix.

## Product ideas

- [ ] **On-screen conversation transcript.** There is currently no way to see what the app heard or replied — mishears are invisible, which reads as "the AI is confused" even when it's an STT problem. Show a lightweight running transcript (last few user/assistant turns, text already available client-side) on the home screen under the button. No backend change; also a trust win for debugging estimation quality (you can see exactly what text the model received).
- [ ] **Online nutrition lookup — deliberately not now.** A web search per food adds seconds of latency to a live voice turn plus per-search cost, and the problem foods that motivated this (homemade/butcher dishes) aren't in databases anyway — model knowledge + deterministic math is the real lever. Revisit only if branded/packaged foods with barcodes/labels become a frequent use case.
- [ ] **Prefetch the profile name on app load** instead of on tap, to shave the small delay before the greeting starts speaking.
- [ ] **Route local error phrases through ElevenLabs too.** "Sorry, I didn't catch that" and "Something went wrong, try again" still use the browser's `speechSynthesis` instead of ElevenLabs like everything else — a deliberate original decision (zero-network-dependency for exactly these phrases) that the user wants revisited. Doable — synthesize these phrases server-side same as the greeting. Whoever picks this up should decide consciously whether to keep a `speechSynthesis` fallback specifically for when the network itself is down.
- [ ] **More liberal `end_conversation` triggering.** The tool exists for closing remarks ("goodbye", "that's all") but may not reliably trigger on a bare "thanks" said after a completed action today. Tune the system-prompt guidance to be more liberal about closing-phrase detection — builds on existing architecture, no new mechanism needed. (A hard silence-timeout was considered and rejected — it would end conversations mid-thought during normal pauses, contradicting the app's "session stays open until the user ends it" design.)

## Engineering hygiene

- [ ] **No README.** Setup steps, env vars, run commands, browser requirements. (`DEPLOY.md` covers the *deployment* half; local dev setup still isn't written down anywhere.)
- [ ] **No test infrastructure in `web/` at all.** The conversation state machine's ordering guarantees (permission before speech, echo-guard epochs, no listening while the AI talks) aren't permanently testable yet — adding Playwright is the obvious way to get there.
- [ ] **Backend tests only cover the tool loop.** `npm test` (root, or `--prefix server`) runs Node's built-in test runner via `tsx` over `server/test/`. Still untested: `truncatePairSafe` ([sessions.ts](server/src/sessions.ts)) and `computeTargets` ([profile.ts](server/src/profile.ts)) — the test infrastructure to cover them is already in place, so these are a short job for whoever picks them up.
