## Multi-user support (shipped 2026-08-24)

- [x] **Real per-user data isolation, not just a second password.** `ACCESS_CODES` env var (replaces `ACCESS_CODE`) maps each shared code to a `user_id` — `andrei23:andrei,Maria:maria` currently. Every table/query now scoped by that identity: `food_entries` gained a `user_id` column, `user_profile`'s old `id INTEGER PRIMARY KEY CHECK (id = 1)` singleton (which made a second profile row *impossible*, not just unused) was rebuilt as `id TEXT PRIMARY KEY` keyed by user_id. Threaded through every layer: `resolveUser` middleware in [index.ts](server/src/index.ts) sets `res.locals.userId`, down through `entries.ts`/`profile.ts` (every query), `tools.ts` (`executeTool`), `chat.ts` (`runTurn`), `systemPrompt.ts` (`buildSystemPrompt`). Frontend needed zero changes — the access-code UI already worked exactly as needed; identity resolution is entirely server-side.
- **Real risk, handled carefully**: this ran a live schema migration against production data holding the user's actual health profile and food log — not a throwaway table. Verified locally first (existing data intact under the default identity with no `ACCESS_CODES` set), then in production immediately after deploy via direct `curl` against both codes before declaring done, not just a green build. All pre-existing data (profile + all entries) confirmed to have survived the `user_profile` table rebuild intact.
- **Cross-user access verified actually blocked, not just hidden**: attempted deleting Andrei's entry using Maria's code → 404 (same response as a genuinely nonexistent ID — no information leak about what exists under another identity). `updateEntry`/`deleteEntry` scope by `user_id` directly in the SQL `WHERE`, not just in what gets listed.
- **One deploy-ordering thing worth remembering for next time**: set the new env var (`ACCESS_CODES`) on Railway *before* deploying the code that depends on it, not after — otherwise there's a real window where the old `ACCESS_CODE` var is inert (code no longer reads it) and the new one doesn't exist yet, meaning the app briefly requires *no* access code at all. Done correctly this time, but easy to get backwards.
- [ ] **Old `ACCESS_CODE` var still sits unused on Railway** — harmless (nothing reads it anymore) but hasn't been explicitly removed; `railway variables` has no discovered unset command yet. Minor cleanup, not urgent.
- **Scale of "multi-user" here**: env-var-based code→identity mapping, not a real accounts system — adding a third person means editing the env var and redeploying, not a signup flow. Deliberately matches the app's existing minimal-auth philosophy for "a couple of trusted people," not built to scale further than that.

## Bugs

- [ ] **Tool-loop exhaustion corrupts session history.** If a `/chat` turn burns all `MAX_TOOL_ITERATIONS` (5) without the model reaching `end_turn`, [chat.ts](server/src/chat.ts) saves history ending in dangling tool results with no closing assistant message, and returns a fabricated "Okay." reply. The next turn on that session can then fail or behave oddly. Fix: on exhaustion, append a synthetic assistant close to history and return a real spoken fallback ("Sorry, that got complicated — can you try again?").
- [ ] **`raw_transcript` doesn't store what the user actually said.** Spec defines it as "what the user actually said," but `log_food`'s dispatch in [tools.ts](server/src/tools.ts) falls back to the model's cleaned `description` when the model doesn't pass `raw_transcript` explicitly (which it never does, since it's not a documented input to the tool). Fix: thread the real `user_text` from `runTurn` down into `executeTool`/`createEntry`.

## Romanian support (shipped 2026-08-24)

- [x] New `language: "en" | "ro"` profile field (nullable, defaults to English behavior). Set via the Profile page or by voice ("switch me to Romanian" → `update_profile`). Drives three things together, always resolved from the same `resolveVoiceId`/`resolveSpeechLang` helpers in [profile.ts](server/src/profile.ts) so they can never drift out of sync: `SpeechRecognition.lang` (`ro-RO` vs `en-US`), the ElevenLabs voice used for synthesis, and an explicit system-prompt instruction telling Haiku to reply in Romanian.
- **Real constraint, not a shortcut**: `SpeechRecognition.lang` must be set *before* `.start()` — the Web Speech API has no per-utterance auto-detect. This is a persisted preference, not seamless mid-sentence code-switching between languages. A user can say "switch to Romanian" mid-conversation and it takes effect starting with that reply/next listen (both `/chat` and `/greeting` return a `lang` field the frontend refreshes into `languageRef` every turn) — but freely mixing English and Romanian turn-by-turn without an explicit switch isn't supported by this API.
- ElevenLabs' `eleven_flash_v2_5` (already in use) is multilingual and speaks Romanian natively — no model change needed. `ELEVENLABS_VOICE_ID_RO` env var (optional) lets a dedicated Romanian-sounding voice be configured; defaults to reusing `ELEVENLABS_VOICE_ID` via the multilingual model if unset. Picking a specific voice is a listen-and-judge call, same as the earlier general voice question.
- Verified end-to-end locally: profile set to `ro` → `/greeting` returns "Bună, Andrei!" with `ro-RO`/real audio → spoken Romanian food-logging text ("am mancat doua oua") correctly parsed, logged, and replied to in natural Romanian. Caught and fixed one real bug in the process: `log_food`'s `description` field was staying in English regardless of conversation language until the tool description was updated to say "write it in the same language you're conversing in."
- **Also caught and fixed before it shipped**: the `language` column migration (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`) crashed the whole server — the SQLite build `node:sqlite` bundles here doesn't support that syntax. Replaced with a `PRAGMA table_info` existence check first. Worth remembering for any future schema migration on this stack: don't assume `IF NOT EXISTS` column syntax works, verify locally first.
- Local error phrases ("Sorry, I didn't catch that") still speak in English regardless of profile language — same intentional-scope-boundary reasoning as the ElevenLabs greeting decision before it was extended: low effort to add later, not done now.

## Voice quality (ElevenLabs, shipped 2026-08-24)

- [x] **Real AI replies now use ElevenLabs TTS** (`eleven_flash_v2_5`, ~75ms synthesis, 50% cheaper per-char than the default model) instead of the browser's `speechSynthesis`. Backend synthesizes audio for `reply_text` after the tool loop finishes ([tts.ts](server/src/tts.ts)), returns it base64-encoded in `/chat`'s response, frontend plays it via a real `<audio>` element ([synthesis.ts](web/src/speech/synthesis.ts)). Verified end-to-end against production: real MP3 returned, correctly decodes, and a manual `<audio>`+data-URL test in the browser confirmed the full `loadedmetadata → canplay → playing → pause → ended` event sequence fires correctly — the exact mechanic the echo-guard's `onEnd` callback depends on.
- [x] **Greeting now uses ElevenLabs too** — fixed 2026-08-24 after the user noticed the inconsistency (greeting sounded robotic, replies didn't). New `GET /greeting` endpoint computes `Hello ${name}` server-side and synthesizes it through the same `tts.ts` used for replies, gated by the same `ACCESS_CODE` middleware. Frontend fetches it via `fetchGreeting()` instead of `fetchProfile()` in `useConversation.ts`, reusing the exact same `speakThenListen(text, audioBase64)` pass-through already built for replies — same fallback-to-`speechSynthesis` guarantee if the call fails.
- **Local error phrases still intentionally stay on `speechSynthesis`** ("Sorry, I didn't catch that", "Something went wrong") — zero-network-dependency by original design (spec §9). User wants this revisited — see "Requested changes" below.
- **Graceful degradation is built in**: if `ELEVENLABS_API_KEY` is unset, or any call fails, both `/chat` and `/greeting` still return their text with `audio_base64: null`, and the frontend automatically falls back to `speechSynthesis` — never a broken turn.

Reply audio plays correctly on-device; the theoretical mobile autoplay-block concern didn't materialize in practice (or the fallback silently handled it — either way, no reported issue).
- **Real recurring cost, not "fractions of a cent"**: ElevenLabs' free tier blocks API voice access entirely (hard 402, not a quota issue) — a paid plan is required. Still modest for personal use, but a genuine departure from the original spec's near-zero framing.

## Nutrition accuracy (composition-ratio rule, shipped 2026-08-24)

- [x] **Fat/lean composition breakdown calculated realistically, not naively.** When the user gives a ratio like "60% fat, 40% meat" alongside a total weight, [systemPrompt.ts](server/src/systemPrompt.ts) instructs the model to split the weight by the ratio, then: fat weight × 9 cal/g directly (adipose tissue genuinely is mostly fat by weight), but lean/meat weight × a realistic protein fraction (~20-30% depending on prep) × 4 cal/g — never the full lean weight × 4. Motivated by "pastramă de oaie" (Romanian grilled sheep pastrami) being unusually fat-heavy; no food database has one authoritative value for a homemade/butcher-cut dish like this, so the ratio math is the real accuracy lever, not a better database (see the "database" conversation this came out of).
- **First version (naive, superseded same day) treated the full lean weight as pure protein** — e.g. 100g "lean meat" logged as 100g protein, 400 cal from that component alone. Real muscle tissue is ~70-75% water, not protein, by weight. This was caught by comparing against ChatGPT's independent estimate for the same dish, which itself lined up almost exactly with eatntrack.ro's real reference value (900 kcal for 250g) — the naive rule was giving 1750 kcal, roughly double. Revised to apply a realistic protein fraction to the lean component; the naive version's math is preserved above only as a record of what didn't work and why.
- **Also matters for protein tracking, not just calories**: the naive rule was inflating logged `protein_g` by roughly 4x for any composition-described dish, which directly undermines the profile's "avoid losing muscle while cutting" goal tracking — a nutrition-accuracy bug with real downstream effect on a feature the user specifically cares about, not just a cosmetic calorie-number issue.
- **Still not perfectly consistent run-to-run** — across all tests of the revised rule (2 local, 2 production), it applied correctly 3 of 4 times; the one miss reverted to the old naive math instead of the nuanced calculation. Same inconsistency pattern as the first rule version, now observed twice across two different rule texts — this looks like a real characteristic of asking Haiku to reliably apply a conditional multi-step calculation, not a wording problem specific to either version. The rule's "confirm out loud" requirement remains the safety net. **Recommended, not yet applied**: lowering the model's `temperature` (currently unset/default, config.ts has no temperature param) to ~0.3-0.4 would likely improve consistency on this and any other conditional instruction, at some cost to conversational variety — offered to the user twice now, still awaiting a decision on whether to apply it globally.

## Requested changes (not yet implemented, 2026-08-24)

- [ ] **Route local error phrases through ElevenLabs too.** User wants "Sorry, I didn't catch that" and "Something went wrong, try again" to use the ElevenLabs voice like everything else, instead of the browser's `speechSynthesis`. This reverses a deliberate original decision (spec §9's zero-network-dependency reasoning for exactly these phrases — an error path that itself depends on the network being up is a real regression risk, especially "something went wrong" which often fires *because* the network is the problem). Doable — synthesize these phrases server-side same as the greeting, or accept the tradeoff and have the frontend call `/greeting`-style endpoints for canned text. Whoever picks this up should decide consciously whether to keep a `speechSynthesis` fallback specifically for the case where the network itself is down (arguably the one case where the original reasoning still applies even after this change).
- [ ] **Auto-end the conversation after the user signals they're done, or after a silence timeout.** User's own suggestion: end after ~3 seconds of silence, or when they say something like "thank you." **Flagging a real conflict before this gets built**: a hard silence-timeout would directly contradict an explicit original spec decision (§2.9: "There is no automatic single-turn cutoff; the session stays open like a real conversation until the user chooses to end it") and our own no-speech handling, which deliberately treats silence as normal (reopens the mic silently, never ends the session) — a blind 3-second cutoff would end conversations mid-thought during any normal pause. The `end_conversation` tool already exists specifically for closing remarks ("goodbye", "that's all") but may not reliably trigger on a bare "thank you" today, since that phrase alone doesn't unambiguously signal the user is done (could be thanking the AI for one specific action mid-conversation). **Recommended approach for whoever implements this**: tune the `end_conversation` tool's system-prompt guidance to be more liberal about closing-phrase detection ("thanks", "okay perfect", "cool thanks" said after a completed action) rather than adding a silence-timeout, since that path builds on existing architecture instead of overriding a documented design principle.

## Deployment

- [x] **Live on Railway as of 2026-08-24**: https://deep-blue-production.up.railway.app — persistent volume at `/data` for SQLite, `ACCESS_CODE` gate, single service serving both API and built frontend. Verified in production: `/health`, `/entries` (401 without the code, 200 with it), `/chat` (full tool loop against real Claude), and the frontend shell all confirmed working against the live URL.
- [ ] **Postgres** — still on SQLite. Fine for single-user; revisit only if multi-device write contention ever becomes a real issue (unlikely at this scale).
- [ ] **Redeploy workflow** — `railway up` from `D:\DeepBlue` after any future change (see DEPLOY.md). Not yet automated (no GitHub-connected auto-deploy-on-push).
- **Not a bug, but a real gotcha**: local dev (`localhost:3001`) and the Railway deployment are two *entirely separate* SQLite databases. Entries logged locally never appear on the deployed URL and vice versa. Bit us **twice** (2026-08-24): first 3 food entries logged locally, then separately the entire `user_profile` row (name, height, weight, goals) — set up via curl/UI against local dev before Railway existed, never migrated, silently leaving production's personalized-recommendation feature running with no profile for hours until the greeting bug surfaced it. Both fixed via `railway ssh` (see below). **From now on, use the deployed URL for anything real — local dev is for testing code changes only, and any local data entered by mistake needs an explicit migration step, it does not appear on its own.**
- SSH access to the Railway container is set up (`~/.ssh/id_ed25519`, registered via `railway ssh keys add`, host key trusted via `ssh-keyscan ssh.railway.com`) — useful for any future one-off maintenance directly against the production SQLite file, e.g. `cat script.js | railway ssh -- node`.
