# Deep Blue — Backlog

Improvements identified in review, not yet implemented. Ordered by priority within each group.

## P0 — Conversation-killing bugs (full-codebase review, 2026-08-25)

**Shipped 2026-08-25** (commit eb94ccb, deployed to Railway; checked items were fixed in that pass — real-device verification of the mic/echo fixes still pending on the phone). Root causes for the two live bug reports ("model doesn't hear me after allowing the mic"; "going to dashboard stops the listening"; "Romanian glitches while speaking"). All three trace to two defects.

- [x] **Dead mic after every `no-speech` restart — THE "doesn't hear me" bug.** The browser fires `error("no-speech")` *then* `end`. `handleRecognitionError` reacts to the error by calling `openMic()` immediately — but [recognition.ts](web/src/speech/recognition.ts) `start()` begins with `if (this.listening) return;`, and `listening` is only reset in the `end` handler, which hasn't fired yet. So the restart silently no-ops, the old recognition's `onEnd` then fires into a handler that does nothing, and the app sits on "Listening…" with no recognition running — permanently deaf. **Every conversation dies at the first ~8s pause.** This explains both reports: first-time users pause after the greeting/permission dance (or start talking *during* the greeting and only the tail reaches the mic → no-speech), and the dashboard case is just "user went quiet while reading." Fix in `SpeechRecognizer.start()`: if an instance is still winding down, `abort()` it and start fresh instead of returning (the epoch guard in useConversation already discards stale events, so this is safe). Additionally make `onEnd` in [useConversation.ts](web/src/conversation/useConversation.ts) a safety net instead of a no-op: if recognition ends while phase is still "listening" on the current epoch (happens when the browser kills recognition with no error — backgrounding, tab switch, phone lock), treat it as no-speech and reopen. When fixing, confirm the error→end event ordering with a one-line `console.log` instrumentation first.
- [x] **TTS watchdog cuts off reply audio and opens the mic into the AI's own voice — the Romanian "glitch."** [synthesis.ts](web/src/speech/synthesis.ts) `playRemoteAudio` estimates duration at 14 chars/sec; when actual speech is slower (Romanian consistently, long English replies sometimes), the watchdog's `finish` fires mid-playback, **does not pause the audio**, and triggers `onEnd` → `openMic()` — so the mic transcribes the tail of the AI's own reply and submits it as a user turn, derailing the conversation. Fix: once `loadedmetadata` fires, re-arm the watchdog from the element's real `duration` (+ ~2s slack) instead of the character estimate, and make a watchdog-triggered `finish` call `el.pause()` before `onEnd`. Same defect in `speakLocal`: its watchdog force-finishes without `speechSynthesis.cancel()`. **Do this before deciding anything about Romanian** — the language support itself (voice/STT/prompt threading via `resolveVoiceId`/`resolveSpeechLang`) is sound; the glitch is this echo bug. If Romanian still misbehaves after the fix, next lever is a dedicated Romanian voice via `ELEVENLABS_VOICE_ID_RO` (currently falls back to the English "Rachel" voice, which is serviceable but not native-sounding). Only remove the language if it still fails after both.
- [x] **Decide and implement what a conversation does when the user navigates away mid-session.** Today, switching to Dashboard/Profile keeps the session technically alive (the hook lives in App.tsx) but invisible: no phase indicator, no interim transcript, no end button — and with the dead-mic bug it silently dies anyway. Once the mic bug is fixed, pick one deliberately: **(a) recommended — conversation persists, with a small floating status pill on every view** (phase + tap to end), matching the natural "log food, then glance at my dashboard while still talking" flow; or (b) navigation ends the session cleanly with a spoken goodbye. Either is fine; the current silent limbo is not.

## P1 — Conversational UX quality (review, 2026-08-25)

- [x] **Barge-in: tap to interrupt while the AI is speaking.** Currently a tap during "speaking"/"thinking" is a no-op (spec's MVP scope), so a long reply can't be cut short and anything you say during it is lost — which also worsens the first-greeting bug above. Implement: tap during "speaking" → `cancelSpeech()` + `openMic()`. The echo-guard epochs already make this safe.
- [x] **`speechSynthesis` fallback speaks Romanian text with an English voice.** `speakLocal` never sets `utterance.lang`, so whenever ElevenLabs is down/unconfigured and the profile is Romanian, replies are read as English-phoneme gibberish. Thread the current lang (the frontend already tracks `languageRef`) into `speak()` and set `utterance.lang` + a matching voice from `getVoices()` when available. (Related, already filed below: route canned error phrases through ElevenLabs / localize them.)
- [ ] **On-screen conversation transcript.** There is currently no way to see what the app heard or replied — mishears are invisible, which reads as "the AI is confused" even when it's an STT problem. Show a lightweight running transcript (last few user/assistant turns, text already available client-side) on the home screen under the button. No backend change. Big trust win for debugging estimation quality too — you can see exactly what text the model received.
- [x] **Auto-idle after sustained silence, not a hard cutoff.** With the dead-mic bug fixed, silence would loop the mic forever (battery + recording indicator pinned on). After ~4 consecutive `no-speech` cycles (~30s of nothing), speak a brief "I'll be here when you need me" and return to idle. This respects spec §2.9 (no mid-conversation cutoff — normal pauses just recycle silently) while ending demonstrably dead sessions. **Supersedes the "Auto-end the conversation" item under Requested changes below** — that item's 3-second-silence idea would cut off normal thinking pauses; this version only ends sessions nobody is in. Keep its other half (more liberal `end_conversation` triggering on "thanks, that's all") as prompt tuning.
- [x] **Stop the conversation when the access gate appears.** When a rotated/invalid code causes a 401 mid-session, `AccessGate` replaces the UI but the conversation keeps speaking/listening behind it. Wire `ACCESS_CODE_INVALIDATED_EVENT` in [App.tsx](web/src/App.tsx) to also call `conversation.endSession()`.
- [x] **Cache the greeting audio server-side.** `/greeting` synthesizes "Hello Andrei" through ElevenLabs on every single session start — recurring credit burn and ~300ms latency for a string that changes only when the name/language changes. In-memory `Map` keyed by `(text, voiceId)` in [index.ts](server/src/index.ts) or [tts.ts](server/src/tts.ts). Pairs with the existing "prefetch the greeting on app load" item under UX polish.

## P2 — Estimation accuracy (review, 2026-08-25)

The observed ~75% rule-application consistency (see Nutrition accuracy section) has two compounding causes: a multi-step arithmetic rule expressed as prose, and a small model executing it. Attack both:

- [ ] **Move the composition math out of English prose into deterministic code — the real consistency fix.** LLMs are unreliable at conditional arithmetic-in-prose but excellent at structured extraction. Extend `log_food` in [tools.ts](server/src/tools.ts) with optional fields (`total_weight_g`, `fat_ratio_pct`, `preparation: raw|cooked|cured`), compute the fat/lean calorie+macro split server-side in `executeTool` — same math, every time, unit-testable. The giant ~250-word composition rule in [systemPrompt.ts](server/src/systemPrompt.ts) then shrinks to two lines ("when the user gives a fat/lean ratio and weight, pass these fields; the tool computes the split — state the returned total out loud"). Shrinking the prompt also measurably helps the model follow every *other* rule.
- [x] **Upgrade the model to Sonnet — recommended, real numbers.** `MODEL` in [config.ts](server/src/config.ts) is one constant. Pricing per million tokens: Haiku 4.5 $1 in / $5 out; Sonnet 5 (`claude-sonnet-5`) $3 / $15 — exactly 3×. This app's turns are small (system+tools ≈ 1.3K tokens, capped history, 1–3 API calls per turn ≈ 5K in / 300 out per logging turn): **Haiku ≈ 0.5–1¢ per turn, Sonnet ≈ 1.5–3¢.** At heavy personal use (15 turns/day): Haiku ≈ $3/mo, Sonnet ≈ $9/mo — roughly +$6/mo, about the price of the ElevenLabs subscription, for visibly better instruction-following and estimation judgment. (Opus 5 at $5/$25 exists as the premium tier — ~5× Haiku — overkill here.) Sonnet 5 has intro pricing ($2/$10) through 2026-08-31. Do this *with* the deterministic-math item, not instead of it.
- [ ] **General prompt cleanup after the above.** [systemPrompt.ts](server/src/systemPrompt.ts) rules are sound but top-heavy; once the composition rule collapses, re-read the remaining rules and trim to short imperative bullets. The user's instinct that "some rules confuse the model" is most true of the one long rule — the rest (estimate-don't-interrogate, always-confirm-aloud, get_entries-before-referencing) are pulling their weight and should stay.
- [ ] **Online nutrition lookup — deliberately not now.** A web search per food adds seconds of latency to a live voice turn plus per-search cost, and the problem foods that started this (homemade/butcher dishes like pastramă) aren't in databases anyway — model knowledge + deterministic math is the actual lever. Revisit only if branded/packaged foods with barcodes/labels become a frequent use case.

## P2 — Correctness & robustness (review, 2026-08-25; complements existing Robustness section)

- [x] **Day boundaries use the server's timezone (UTC on Railway), not the user's (UTC+2/+3 Romania).** [entries.ts](server/src/entries.ts) `date(created_at, 'localtime')` resolves against the container's UTC clock, while the Dashboard header shows the user's local date. Anything logged 00:00–03:00 Romania time lands on the *previous* day, and "what did I eat today" asked at 1am reads out yesterday. Cheapest real fix: set `TZ=Europe/Bucharest` on the Railway service (one env var, zero code). Proper fix if multi-timezone users ever matter: client sends its date/offset explicitly.
- [x] **History cap counts raw messages, not turns — the model forgets fast.** `MAX_HISTORY_MESSAGES = 20` in [config.ts](server/src/config.ts), but tool-heavy turns emit 4–11 messages each (assistant tool_use + user tool_result pairs), so real memory is ~3–5 user turns, not the intended 20 pairs (spec §7). Make `truncatePairSafe` in [sessions.ts](server/src/sessions.ts) count genuine user turns when choosing the cut point, or raise the constant to compensate.
- [ ] **No rate limiting on auth or paid endpoints.** Access codes are low-entropy by design ("andrei23"), the URL is public, and every `/chat`/`/greeting` hit burns real Anthropic/ElevenLabs money. Add a simple per-IP throttle (e.g. `express-rate-limit`): tight on 401 responses (brute-force), loose on authenticated traffic.

## Multi-user support (shipped 2026-08-24)

- [x] **Real per-user data isolation, not just a second password.** `ACCESS_CODES` env var (replaces `ACCESS_CODE`) maps each shared code to a `user_id` — `andrei23:andrei,Maria:maria` currently. Every table/query now scoped by that identity: `food_entries` gained a `user_id` column, `user_profile`'s old `id INTEGER PRIMARY KEY CHECK (id = 1)` singleton (which made a second profile row *impossible*, not just unused) was rebuilt as `id TEXT PRIMARY KEY` keyed by user_id. Threaded through every layer: `resolveUser` middleware in [index.ts](server/src/index.ts) sets `res.locals.userId`, down through `entries.ts`/`profile.ts` (every query), `tools.ts` (`executeTool`), `chat.ts` (`runTurn`), `systemPrompt.ts` (`buildSystemPrompt`). Frontend needed zero changes — the access-code UI already worked exactly as needed; identity resolution is entirely server-side.
- **Real risk, handled carefully**: this ran a live schema migration against production data holding the user's actual health profile and food log — not a throwaway table. Verified locally first (existing data intact under the default identity with no `ACCESS_CODES` set), then in production immediately after deploy via direct `curl` against both codes before declaring done, not just a green build. All pre-existing data (profile + all entries) confirmed to have survived the `user_profile` table rebuild intact.
- **Cross-user access verified actually blocked, not just hidden**: attempted deleting Andrei's entry using Maria's code → 404 (same response as a genuinely nonexistent ID — no information leak about what exists under another identity). `updateEntry`/`deleteEntry` scope by `user_id` directly in the SQL `WHERE`, not just in what gets listed.
- **One deploy-ordering thing worth remembering for next time**: set the new env var (`ACCESS_CODES`) on Railway *before* deploying the code that depends on it, not after — otherwise there's a real window where the old `ACCESS_CODE` var is inert (code no longer reads it) and the new one doesn't exist yet, meaning the app briefly requires *no* access code at all. Done correctly this time, but easy to get backwards.
- [ ] **Old `ACCESS_CODE` var still sits unused on Railway** — harmless (nothing reads it anymore) but hasn't been explicitly removed; `railway variables` has no discovered unset command yet. Minor cleanup, not urgent.
- **Scale of "multi-user" here**: env-var-based code→identity mapping, not a real accounts system — adding a third person means editing the env var and redeploying, not a signup flow. Deliberately matches the app's existing minimal-auth philosophy for "a couple of trusted people," not built to scale further than that.

## Platform gaps

- [x] **First-run mic permission prompt collided with the greeting** — reported and fixed 2026-08-24. On a phone, the first tap greeted the user ("Hello Andrei") and only *then* opened the mic, which is the moment the browser raises its permission prompt. So the user answered the greeting while the prompt was still up, nothing was capturing, and the words vanished — the app just sat on "Listening…" forever, because the eventual `no-speech` handler silently reopens the mic by design. Fixed by asking for the mic up front in [permission.ts](web/src/speech/permission.ts): `startSession` now fires `getUserMedia` and the greeting fetch together before its first `await`, so the prompt is raised inside the tap's own user gesture and the greeting downloads while the user decides — but **nothing is spoken until permission settles**. New `awaiting-mic` phase shows "Allow mic…" on the button instead of a misleading "Thinking…".
- **The prompt is only requested when it's actually needed**: `navigator.permissions.query({name:"microphone"})` short-circuits the returning-user case, so we don't reopen the capture device (and flash the recording indicator) on every session start. The probe stream's tracks are stopped immediately — holding them would pin the browser's recording indicator on for the whole conversation, since SpeechRecognition opens its own capture anyway.
- **Refusal is now handled before anything is spoken** rather than after: the help card appears immediately, and it has a "Try again" button, because the most likely cause on mobile is a *dismissed* prompt (recoverable by re-asking) rather than a permanent block. Its copy no longer assumes a desktop address bar.
- **Verified in a real browser, both directions.** Drove the built app in headless Chromium with `getUserMedia`, `speechSynthesis.speak`, `<audio>.play` and `SpeechRecognition` instrumented to timestamp the actual ordering. Pre-fix timeline reproduced the report exactly: `app speaks: Hello there → mic opened → PERMISSION PROMPT APPEARS`. Post-fix: `mic-prompt-shown → answered → track released → spoke greeting → mic opened for listening`, with nothing spoken during the prompt window. Also checked the already-granted path (no device reopen) and the refusal path (nothing spoken, help card shown). **Not committed** — it needs Playwright, which the repo doesn't depend on; `web/` still has no test infrastructure (see Engineering hygiene). Reproducing it is ~60 lines against `localhost` if it's ever needed again.
- **Untested on iOS specifically**: the fix is plain `getUserMedia`, which iOS supports, but iOS may additionally gate *speech recognition* separately from the microphone. If a second prompt ever shows up there, the greeting no longer collides with the mic one either way — worth a real-device check next time the app is opened on the iPhone.

- ~~iPhone can't use voice conversation~~ — **correction 2026-08-24**: confirmed working on the user's actual iPhone (Chrome) against the Railway deployment. The claim that WebKit lacks `SpeechRecognition` support was either outdated or wrong; not re-litigating it without evidence either way. If it ever misbehaves on iOS again, don't assume it's the old WebKit limitation — investigate fresh.

## Romanian support (shipped 2026-08-24)

- [x] New `language: "en" | "ro"` profile field (nullable, defaults to English behavior). Set via the Profile page or by voice ("switch me to Romanian" → `update_profile`). Drives three things together, always resolved from the same `resolveVoiceId`/`resolveSpeechLang` helpers in [profile.ts](server/src/profile.ts) so they can never drift out of sync: `SpeechRecognition.lang` (`ro-RO` vs `en-US`), the ElevenLabs voice used for synthesis, and an explicit system-prompt instruction telling Haiku to reply in Romanian.
- **Real constraint, not a shortcut**: `SpeechRecognition.lang` must be set *before* `.start()` — the Web Speech API has no per-utterance auto-detect. This is a persisted preference, not seamless mid-sentence code-switching between languages. A user can say "switch to Romanian" mid-conversation and it takes effect starting with that reply/next listen (both `/chat` and `/greeting` return a `lang` field the frontend refreshes into `languageRef` every turn) — but freely mixing English and Romanian turn-by-turn without an explicit switch isn't supported by this API.
- ElevenLabs' `eleven_flash_v2_5` (already in use) is multilingual and speaks Romanian natively — no model change needed. `ELEVENLABS_VOICE_ID_RO` env var (optional) lets a dedicated Romanian-sounding voice be configured; defaults to reusing `ELEVENLABS_VOICE_ID` via the multilingual model if unset. Picking a specific voice is a listen-and-judge call, same as the earlier general voice question.
- Verified end-to-end locally: profile set to `ro` → `/greeting` returns "Bună, Andrei!" with `ro-RO`/real audio → spoken Romanian food-logging text ("am mancat doua oua") correctly parsed, logged, and replied to in natural Romanian. Caught and fixed one real bug in the process: `log_food`'s `description` field was staying in English regardless of conversation language until the tool description was updated to say "write it in the same language you're conversing in."
- **Also caught and fixed before it shipped**: the `language` column migration (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`) crashed the whole server — the SQLite build `node:sqlite` bundles here doesn't support that syntax. Replaced with a `PRAGMA table_info` existence check first. Worth remembering for any future schema migration on this stack: don't assume `IF NOT EXISTS` column syntax works, verify locally first.
- Local error phrases ("Sorry, I didn't catch that") still speak in English regardless of profile language — same intentional-scope-boundary reasoning as the ElevenLabs greeting decision before it was extended: low effort to add later, not done now.

## Nutrition accuracy (composition-ratio rule, shipped 2026-08-24)

- [x] **Fat/lean composition breakdown calculated realistically, not naively.** When the user gives a ratio like "60% fat, 40% meat" alongside a total weight, [systemPrompt.ts](server/src/systemPrompt.ts) instructs the model to split the weight by the ratio, then: fat weight × 9 cal/g directly (adipose tissue genuinely is mostly fat by weight), but lean/meat weight × a realistic protein fraction (~20-30% depending on prep) × 4 cal/g — never the full lean weight × 4. Motivated by "pastramă de oaie" (Romanian grilled sheep pastrami) being unusually fat-heavy; no food database has one authoritative value for a homemade/butcher-cut dish like this, so the ratio math is the real accuracy lever, not a better database (see the "database" conversation this came out of).
- **First version (naive, superseded same day) treated the full lean weight as pure protein** — e.g. 100g "lean meat" logged as 100g protein, 400 cal from that component alone. Real muscle tissue is ~70-75% water, not protein, by weight. This was caught by comparing against ChatGPT's independent estimate for the same dish, which itself lined up almost exactly with eatntrack.ro's real reference value (900 kcal for 250g) — the naive rule was giving 1750 kcal, roughly double. Revised to apply a realistic protein fraction to the lean component; the naive version's math is preserved above only as a record of what didn't work and why.
- **Also matters for protein tracking, not just calories**: the naive rule was inflating logged `protein_g` by roughly 4x for any composition-described dish, which directly undermines the profile's "avoid losing muscle while cutting" goal tracking — a nutrition-accuracy bug with real downstream effect on a feature the user specifically cares about, not just a cosmetic calorie-number issue.
- **Still not perfectly consistent run-to-run** *(2026-08-25: root-caused and actioned — see the "P2 — Estimation accuracy" section at the top: move the math into `log_food` server-side + upgrade to Sonnet; those two items replace the temperature-tuning idea below)* — across all tests of the revised rule (2 local, 2 production), it applied correctly 3 of 4 times; the one miss reverted to the old naive math instead of the nuanced calculation. Same inconsistency pattern as the first rule version, now observed twice across two different rule texts — this looks like a real characteristic of asking Haiku to reliably apply a conditional multi-step calculation, not a wording problem specific to either version. The rule's "confirm out loud" requirement remains the safety net. **Recommended, not yet applied**: lowering the model's `temperature` (currently unset/default, config.ts has no temperature param) to ~0.3-0.4 would likely improve consistency on this and any other conditional instruction, at some cost to conversational variety — offered to the user twice now, still awaiting a decision on whether to apply it globally.

## Requested changes (not yet implemented, 2026-08-24)

- [ ] **Route local error phrases through ElevenLabs too.** User wants "Sorry, I didn't catch that" and "Something went wrong, try again" to use the ElevenLabs voice like everything else, instead of the browser's `speechSynthesis`. This reverses a deliberate original decision (spec §9's zero-network-dependency reasoning for exactly these phrases — an error path that itself depends on the network being up is a real regression risk, especially "something went wrong" which often fires *because* the network is the problem). Doable — synthesize these phrases server-side same as the greeting, or accept the tradeoff and have the frontend call `/greeting`-style endpoints for canned text. Whoever picks this up should decide consciously whether to keep a `speechSynthesis` fallback specifically for the case where the network itself is down (arguably the one case where the original reasoning still applies even after this change).
- [ ] **Auto-end the conversation after the user signals they're done, or after a silence timeout.** *(Partially superseded 2026-08-25: see "Auto-idle after sustained silence" under P1 above for the silence half; the closing-phrase prompt tuning below still stands.)* User's own suggestion: end after ~3 seconds of silence, or when they say something like "thank you." **Flagging a real conflict before this gets built**: a hard silence-timeout would directly contradict an explicit original spec decision (§2.9: "There is no automatic single-turn cutoff; the session stays open like a real conversation until the user chooses to end it") and our own no-speech handling, which deliberately treats silence as normal (reopens the mic silently, never ends the session) — a blind 3-second cutoff would end conversations mid-thought during any normal pause. The `end_conversation` tool already exists specifically for closing remarks ("goodbye", "that's all") but may not reliably trigger on a bare "thank you" today, since that phrase alone doesn't unambiguously signal the user is done (could be thanking the AI for one specific action mid-conversation). **Recommended approach for whoever implements this**: tune the `end_conversation` tool's system-prompt guidance to be more liberal about closing-phrase detection ("thanks", "okay perfect", "cool thanks" said after a completed action) rather than adding a silence-timeout, since that path builds on existing architecture instead of overriding a documented design principle.

## Deployment

- [x] **Live on Railway as of 2026-08-24**: https://deep-blue-production.up.railway.app — persistent volume at `/data` for SQLite, `ACCESS_CODE` gate, single service serving both API and built frontend. Verified in production: `/health`, `/entries` (401 without the code, 200 with it), `/chat` (full tool loop against real Claude), and the frontend shell all confirmed working against the live URL.
- [ ] **Postgres** — still on SQLite. Fine for single-user; revisit only if multi-device write contention ever becomes a real issue (unlikely at this scale).
- [ ] **Redeploy workflow** — `railway up` from `D:\DeepBlue` after any future change (see DEPLOY.md). Not yet automated (no GitHub-connected auto-deploy-on-push).
- **Not a bug, but a real gotcha**: local dev (`localhost:3001`) and the Railway deployment are two *entirely separate* SQLite databases. Entries logged locally never appear on the deployed URL and vice versa. Bit us **twice** (2026-08-24): first 3 food entries logged locally, then separately the entire `user_profile` row (name, height, weight, goals) — set up via curl/UI against local dev before Railway existed, never migrated, silently leaving production's personalized-recommendation feature running with no profile for hours until the greeting bug surfaced it. Both fixed via `railway ssh` (see below). **From now on, use the deployed URL for anything real — local dev is for testing code changes only, and any local data entered by mistake needs an explicit migration step, it does not appear on its own.**
- SSH access to the Railway container is set up (`~/.ssh/id_ed25519`, registered via `railway ssh keys add`, host key trusted via `ssh-keyscan ssh.railway.com`) — useful for any future one-off maintenance directly against the production SQLite file, e.g. `cat script.js | railway ssh -- node`.
